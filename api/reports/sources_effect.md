# Как источники данных улучшают прогноз

Отчёт генерируется скриптом `python -m api.reports.sources_effect` (данные — `sources_effect.json`).
Каждый источник подключается через тот же код, что и в API (`Integration.fetch(company) → Event[]`), прогноз строит ядро `cashflow_core`. Метрики: **MAE** — средняя ошибка ожидаемого остатка (P50) за 30 дней, ₽; **покрытие** — доля дней, когда факт попал в диапазон low–high (цель 80%); **разрыв найден** — риск с вероятностью ≥ 50% в пределах ±5 дней от первого дня фактического минуса; **ложная тревога** — риск ≥ 50% там, где минуса не было.

## Б. Бэктест на реальных выписках организаторов — holdout (38 компаний)

Только **отложенные компании** (`api/reports/split.py`; единственный параметр источников — доля налогов от зарплаты — подобран на dev-компаниях). Отсечка — за 30 дней до последней операции; признаки и события считаются только по операциям до отсечки, остатки будущих дней не используются; факт — последние 30 дней. **Налоговый календарь** и **банк** (без своего файла — только графики кредитов и лизинга по истории счёта) не используют будущее — их вклад честный. **1С (имитация)**: учётная система «знает» ~80% будущих поступлений по счетам/договорам с ошибкой даты до ±4 дней — оценка того, сколько даст подключение реальной 1С.

Выводы по реальным данным:

* налоговый календарь — небольшой выигрыш: даты ЕНП и квартальных авансов известны точно, суммы — оценка;
* банк без своего файла (графики кредитов по истории) почти не меняет прогноз — ядро и так находит эти платежи;
* имитация 1С **ухудшает** прогноз: ядро v0.1 добавляет известные поступления по счетам сверх своего остаточного ряда выручки (в котором эти же клиенты уже есть) — деньги учитываются дважды. Нужна доработка в `core/`: событие от контрагента должно вычитать его долю из остаточного потока (как это уже сделано для регулярных платежей в пределах ±7 дней). На демо-компаниях (часть А) выигрыш от 1С есть, потому что ключевой клиент — регулярный платёж, и событие его заменяет.

## Как источник влияет на прогноз

| источник | что даёт | как учитывается |
|---|---|---|
| налоговый календарь (`tax_calendar`) | ЕНП до 28-го, авансы УСН, НДС тремя частями, налог на прибыль; режим — из настроек или по выписке | событие `tax` на дату срока (перенос с выходных), сумма — оценка по выписке с расшифровкой в `note`; заменяет налоговый всплеск из истории |
| банк (`bank`) | графики кредитов, ведомости зарплатного проекта, созданные/подписанные платёжки | точные даты и суммы обязательных платежей (`loan`, `payroll`, `contract`/`invoice`) |
| 1С (`1c`) | счета покупателям и от поставщиков, договоры, ведомости | неоплаченный счёт — `expected`/`overdue`; просроченный → ядро закладывает высокую вероятность задержки; платежи, которых нет в истории (годовые лицензии, акты субподрядчиков) |
| договоры (`contracts`) | график, предоплата, отсрочка | события `contract` по графику: предоплата при подписании, остаток после поставки + отсрочка |
| счета (`invoices`) | выставленные/полученные счета с датой и сроком | события `invoice` на срок оплаты на неоплаченный остаток |
| открытые реестры (`registry`) | долги по налогам, суды, ФССП, банкротство контрагента; госконтракты | контрагент с высоким риском → его поступления сдвигаются (сценарий `client_delay` ядра), причина — в `warnings` и `note`; этапы госконтрактов — события `contract` |
| ручной ввод (`manual`) | «клиент обещал 300 000 ₽ 20-го», «в декабре куплю оборудование» | событие `manual` (форма или разбор фразы `/events/parse`) |

## Ограничения и что дальше

* Если ожидаемую оплату регулярного клиента перенести вручную дальше чем на 7 дней от его обычной даты, ядро (v0.1) оставляет и регулярный платёж, и событие — деньги учитываются дважды. Для реестров API обходит это сценарием `client_delay`; для ручного переноса нужна доработка сопоставления событий с регулярными платежами в `core/`.
* Суммы налогов — оценка по выписке: для ОСНО НДС считается по выделенному в назначениях НДС, налог на прибыль — грубо (маржа ≤ 15%).
* Открытые реестры и 1С в прототипе — мок-адаптеры с тестовыми данными; подключение реальных API — замена метода `fetch`/`load`.
