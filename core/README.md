# cashflow_core — ядро прогноза остатка и кассовых разрывов

Python-пакет: загрузка выписки → категории → регулярные платежи → прогноз остатка
по дням (P10/P50/P90) → риски кассового разрыва с причиной и рекомендациями →
сценарии «что если» → бэктест.

Зависимости только `numpy`, `pandas`, `scikit-learn`, `matplotlib` (тесты — `pytest`).

## Запуск

```bash
# из корня репозитория
pip install -e core            # или: export PYTHONPATH=core
python -m cashflow_core.demo data/raw/statements/C001.csv
python -m cashflow_core.demo data/raw/all_operations.csv --company C009 --horizon 45
python -m cashflow_core.demo data/raw/statements/C001.csv \
       --scenario '{"type":"client_delay","params":{"counterparty_or_event_id":"Дистрибьютор-489","weeks":3}}'
python -m cashflow_core.demo data/raw/statements/C001.csv --json /tmp/forecast.json

python -m pytest core/tests                 # 44 теста (~1,5 мин)
python core/tests/run_tests.py              # то же без pytest (мини-раннер)

# машинно-читаемый прогноз для контрольного датасета (последняя дата каждой компании → horizon дней)
python -m cashflow_core.predict data/raw/all_operations.csv --horizon 30 --out predictions.csv
#   predictions.csv : company_id;date;balance_forecast;balance_low;balance_high   (разделитель «;»; P50 / P10 / P90)
#   predictions.json: по компаниям — as_of, current_balance, comfort_balance,
#                     risks [{kind: gap|below_comfort, date, shortfall_amount, probability, severity, reason}], warnings, status

# качество на ЛЮБОМ датасете в формате организаторов (папка со statements/*.csv или один CSV):
# 4 подхода («остаток не изменится», наивный, сезонный, гибрид), ошибка по фактическому balance_eod
python -m cashflow_core.evaluate data/raw --workers 4 --split core/reports/split.json --name raw   # → core/reports/evaluate_raw.{json,md}
python -m cashflow_core.evaluate /путь/к/новому/all_operations.csv --workers 8

# имитация контрольного датасета: последние 30 дней каждой выписки — факт, прогноз как у predict
python -m cashflow_core.control data/raw --workers 4 --split core/reports/split.json --name raw    # → core/reports/control_raw.{json,md}

# отчёт для слайдов и экрана «Качество» из двух прогонов выше (цифры holdout)
python -m cashflow_core.report publish      # → metrics.json (формат контракта), metrics.md, errors.png
python -m cashflow_core.report split        # разбиение dev/holdout (core/reports/split.json)
```

## API (контракт)

```python
from cashflow_core import (load_statement, categorize, detect_recurring, forecast,
                           run_scenarios, update_forecast, backtest, compare_models,
                           build_state, forecast_from_state, estimate_tax_regime)

df = load_statement("data/raw/statements/C001.csv")      # DataFrame, df.attrs["warnings"]
cat = categorize(df)                                      # + category, category_label, category_confidence
rec = detect_recurring(cat)                               # [{name, direction, amount_avg, period_days, next_date, confidence}]
res = forecast(df, events=[], horizon=30)                 # ForecastResult (dict)
scn = run_scenarios(df, [], {"type": "revenue_drop", "params": {"percent": 20}})  # {base, scenario, delta}

# Для API выгоднее один раз построить состояние и переиспользовать его:
state = build_state(df, events, horizon=30, company_id="C001")   # ~4 с на 2 года истории
res = forecast_from_state(state)                                  # ~0.05 с
scn = run_scenarios(state, scenario={"type": "unplanned_expense", "params": {"amount": 500000, "date": "2026-10-15"}})
state, res = update_forecast(state, new_rows)                     # новые операции без полного пересчёта
```

Дополнительные необязательные аргументы `forecast`/`build_state`: `company_id`, `n_sims` (2000),
`seed` (42), `threshold` (порог разрыва, 0 ₽), `comfort_balance` (подушка безопасности владельца;
по умолчанию — расходы примерно за 7 дней), `model` (`auto|ets|gbm|naive`), `as_of`,
`interval_scale` (множитель ширины интервалов; по умолчанию подобранный на dev `schema.INTERVAL_SCALE`).

### Формат ответа

`ForecastResult` строго по контракту + необязательные поля контракта `warnings`, `as_of`,
`current_balance`, `daily[].events` (id событий на дату) и `comfort_balance` (подушка безопасности, от которой
считается риск «мало денег»; **новое необязательное поле — на согласование**):

```json
{
  "company_id": "C001", "generated_at": "2026-10-23T17:30:00+00:00", "horizon_days": 30,
  "as_of": "2026-09-29", "current_balance": 1723624.49, "comfort_balance": 517600.0,
  "daily": [{"date": "2026-09-30", "balance_p50": 1861000.0, "balance_low": 1527000.0, "balance_high": 2130000.0}],
  "risks": [{"date": "2026-10-28", "shortfall_amount": 821000.0, "probability": 0.28, "severity": "medium",
             "reason": "28 октября нужно обязательно заплатить налоги за квартал (ЕНП) 505 000 ₽ (оценка по выписке и налоговому календарю) и ...",
             "recommendations": ["Можно перенести оплату поставщику ... на 30 октября или позже ...",
                                 "Если перенести платежи не получится, можно рассмотреть овердрафт или кредит примерно на ..."]}],
  "recurring": [{"name": "Зарплата (~10-го числа)", "direction": "out", "amount_avg": 349926.82,
                 "period_days": 30, "next_date": "2026-10-09", "confidence": 0.985}],
  "sources_used": ["bank"],
  "warnings": []
}
```

* `balance_low` / `balance_high` — P10 / P90 (80% интервал) по 2000 траекториям Monte Carlo.
* Два уровня риска: **кассовый разрыв** (остаток < 0 — не хватит на платежи, в том числе обязательные)
  и **ниже подушки безопасности** (остаток < `comfort_balance`, платежи проходят, но запаса почти нет;
  показывается от 25% и только если в эти дни нет риска разрыва).
* `risks[].probability` — максимальная за эпизод доля траекторий ниже порога.
* `risks[].shortfall_amount` — сколько денег нужно, чтобы закрыть нехватку в 9 случаях из 10.
* `severity` разрыва: high — p ≥ 0.6 (или p ≥ 0.4 в ближайшие 7 дней); medium — p ≥ 0.25; low — от 5%.
  Риск «ниже подушки» — low (medium, если p ≥ 0.6 в ближайшую неделю).
* `reason` — что, когда, сколько и почему; у каждой суммы — источник («регулярный платёж из выписки»,
  «вы ввели», «налоговый календарь», «из 1С»…). `recommendations` — 2–3 варианта действий владельца
  («Можно попросить…», «Можно перенести…», «Если не получится — можно рассмотреть овердрафт на N ₽ на M дней»);
  зарплату и налоги переносить не советуем.
* Коды категорий: `revenue, payroll, rent, taxes, suppliers, utilities, loans, bank_fees, transfers, other`
  (русские названия — `cashflow_core.schema.CATEGORIES`).

`run_scenarios(...)["delta"]`: по контракту `first_gap_date` и `max_shortfall` — значения **для сценария**;
дополнительно `first_gap_date_base`, `max_shortfall_base`, `days_earlier`, `max_shortfall_change`.

## Как устроен прогноз

1. **Очистка** (`io.py`). Колонки распознаются по синонимам (`operation_date→date`,
   `payment_purpose→purpose`, «Поступление/Списание»→in/out, «Дебет/Кредит», знаковая сумма),
   ИНН читается строкой, даты в разных форматах, кодировки utf-8/cp1251, «шапка» над таблицей.
   Дубли удаляются **сверкой с остатком**: если без дубля сумма за день сходится с изменением
   `balance_eod` — это дубль выгрузки (в датасете у дублей разные `operation_id`).
   Расхождения остатка с операциями помечаются в `warnings`.
2. **Категории** (`categorize.py`): правила по назначению (после вырезания «в т.ч. НДС…»),
   затем «память контрагента», затем TF-IDF + логистическая регрессия для пустых/непонятных назначений.
3. **Регулярные платежи** (`recurring.py`): поиск «якорей» — день месяца (до двух: аванс 25-го и
   зарплата 10-го), день недели, квартал; учитывается перенос с выходных/праздников по
   производственному календарю РФ (вперёд для налогов, назад для зарплаты — выучивается из данных).
4. **Налоги** (`taxes.py`): ЕНП 28-го = ежемесячная база + квартальный всплеск, который
   прогнозируется как доля выручки прошлого квартала (доля — по тому же месяцу прошлого года).
   Режим налогообложения оценивается по данным (`estimate_tax_regime`).
5. **Остальные потоки** (`flows.py`): сезонный профиль (уровень × тип дня × «как год назад»)
   или градиентный бустинг — выбирается **по ошибкам прошлых прогнозов на этих же данных**.
6. **Monte Carlo** (`engine.py`): 2000 траекторий; шум сумм, задержки входящих платежей,
   ошибки остаточной модели берутся из реальных ошибок прошлых 30-дневных прогнозов.
   Пополнения «собственными средствами» и займы учредителя в прогноз **не** закладываются:
   прогноз показывает, сколько не хватит, если ничего не делать.
7. **Риски** (`risk.py`), **сценарии** (`scenarios.py`) — из тех же симуляций с общими случайными числами.

## Инкрементальное обновление

`update_forecast(state, new_rows)`: новые строки (список dict / DataFrame / CSV) чистятся тем же
парсером и размечаются уже обученным категоризатором; дубли отбрасываются; остаток сдвигается;
операции сопоставляются с ожидаемыми регулярными платежами и событиями (`paid`), неоплаченные
в срок события получают `overdue` и попадают в `warnings`; модели потоков не переобучаются (берут
продлённую историю как контекст). Полная перестройка — раз в 30 дней новых данных.
На C001: 26 новых операций — 0.13 с против ~4–8 с полного построения. `state.last_update` — что изменилось.

## Качество: честная проверка

* **dev / holdout.** 150 компаний разделены 50/50 внутри каждой отрасли (`core/reports/split.json`,
  порядок по `sha1(seed:company_id)`). Всё, что подбирается (множитель интервалов, выбор вариантов модели),
  подбирается **только на dev**. В отчёт и на слайды идут метрики **только holdout**, посчитанные в
  продуктовой конфигурации после того, как параметры зафиксированы.
* **Rolling origin** внутри компании: на каждой дате отсечения категоризатор, регулярные платежи,
  налоговая модель и модели потоков обучаются заново только на данных до этой даты; прогноз на 30 дней
  сравнивается с фактом. История короче 6 месяцев — до 3 отсечек с минимумом 45 дней обучения.
* **Нет утечки из будущего**: `tests/test_leakage.py` портит все строки после отсечки (суммы ×10, остатки,
  назначения) и проверяет, что прогноз не изменился ни на копейку; стартовый остаток — последний известный
  `balance_eod` до отсечки.
* **`python -m cashflow_core.evaluate <папка|CSV>`** прогоняет весь конвейер на любом датасете того же
  формата (продуктовая конфигурация, без подгонки) и сохраняет MAE/WAPE остатка, ошибку потоков, покрытие
  интервалов, precision/recall разрывов, срок предупреждения, точность регулярных платежей, время и сбои в
  `core/reports/evaluate_<имя>.{json,md}`. Кэш по содержимому выписки — прерванный прогон досчитывается.
* **Цель — фактический остаток.** Ошибка P50 считается относительно `balance_eod`; рядом — бейзлайн
  «остаток не изменится». Прогноз «как есть» ему проигрывал, поэтому финальный P50 — смесь: платежи по
  расписанию (регулярные, налоги) сохраняются полностью, остаточные потоки сжимаются к текущему остатку
  (`schema.SHRINK_SHAPE`, `SHRINK_DRIFT`, подобраны на dev — `core/reports/shrink.json`), интервал
  откалиброван на dev по фактическому остатку (`INTERVAL_SCALE` = 1,25, `calibration.json`).
* Итог на 73 holdout-компаниях — `core/reports/metrics.md`: по общему WAPE модель немного хуже бейзлайна,
  по медиане относительной ошибки — лучше, точнее бейзлайна у большинства компаний (цифры и оговорки — там же).
* Скорость (2 ядра): прогноз компании ~1,8 с; бэктест компании (8 отсечек × 3 модели) ~14 с;
  `evaluate` по 73 компаниям — 9 мин, по всем 150 — ~18–20 мин. Рабочие процессы ограничены одним потоком
  (`parallel.py`), иначе потоки бустинга «дерутся» за ядра и всё замедляется в десятки раз.
* Файлы: `metrics.md` (таблица для слайда и методика), `metrics.json` (раздел 5 контракта), `errors.png`,
  `evaluate_raw.*` (rolling origin, все / dev / holdout), `control_raw.*` (последние 30 дней), `shrink.json`,
  `calibration.json`, `split.json`.

## predict — прогноз без интерфейса

`python -m cashflow_core.predict <CSV | папка> --horizon 30 --out <файл>` (из кода — `cashflow_core.predict.predict(...)`
или `predict_company(cid, df)` для одной компании). Для каждой компании берётся последняя дата её выписки;
модель видит только строки выписки. Детерминированно: seed 42, сортировка по `company_id`, без временных меток —
одинаковый вход даёт побайтно одинаковые файлы при любом `--workers` (проверяет `tests/test_predict.py`).
Не падает: короткая история, пустые ИНН/назначения, одна строка, овердрафт — компания всё равно получает
`horizon` строк; если прогноз построить не удалось, остаток показывается без изменений, `status: "fallback"`,
причина — в `warnings`. Скорость: ~1,8 с на компанию; все 150 компаний датасета — 2 мин 22 с на 2 процессах
(4500 строк, ни одного запасного варианта).

## Без подгонки под датасет

* В правилах и признаках нет `company_id`, конкретных ИНН и названий контрагентов. Категории — по смыслу
  назначения (нормализация текста, вырезание «в т.ч. НДС», синонимы «ЕНП» / «Единый налоговый платёж»)
  и по типу получателя («казначейство», «ФНС» — названия учреждений, а не конкретные компании).
* Всё, что опирается на контрагентов (память контрагента для пустых назначений, группировка регулярных
  платежей, «крупный клиент»), строится **заново по истории самой компании** при каждом вызове.
* Модели подстраиваются под одну компанию на лету (секунды), заранее обученных на датасете компонентов нет;
  все случайные процессы с фиксированным seed.
* Оговорка: тексты правил категоризации писались по формулировкам всего датасета организаторов до
  разделения на dev/holdout, поэтому метрика категоризации на holdout может быть оптимистичной;
  параметры модели прогноза на holdout не подбирались.

## Граничные случаи

История < 14 дней — «минимальный» режим (средние потоки); < 90 дней — упрощённый (без бустинга,
шире интервалы); оба помечаются в `warnings`. Пустой/битый файл, нет колонок, нулевые суммы,
пустые назначения и ИНН, овердрафт (отрицательный старт), один крупный клиент (> 50% выручки),
новый контрагент в событиях, прекратившиеся регулярные поступления — не роняют расчёт, а дают
понятное предупреждение.

## Логи

Логгер `cashflow_core` пишет только счётчики, доли, длительности и id; фильтр дополнительно
маскирует похожие на ИНН и суммы числа.
